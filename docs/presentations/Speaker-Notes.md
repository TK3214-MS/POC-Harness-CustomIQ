# Speaker Notes（発表者向けノート）

> [Executive-Presentation.md](Executive-Presentation.md) と [Technical-Presentation.md](Technical-Presentation.md) のスライド番号に対応した発表者向けノートです。想定質問への回答例と、発表時に避けるべき失敗（誤った印象を与える言い回し）をまとめています。
>
> **発表者が守るべき大原則**: 「Local Preview Mode（合成データ・ローカル実行）でのみ動作確認済み」という事実を、いかなる質問に対してもぼかさずに答えること。Live Adapter が実際に Microsoft 製品の API を呼び出していると誤解させる発言は、意図的であるか否かに関わらず絶対に行わないこと。

## Executive Presentation 発表者ノート

### Slide 1〜3（タイトル・課題設定・コンセプト）

- 話し方: 「業界ごとに AI 基盤を作り直すコスト」という痛みから入り、「基盤は共通、中身だけ差し替える」というコンセプトへ誘導する
- 避けるべき表現: 「導入実績」「本番稼働中」といった、まだ実現していない実績を示唆する言葉

### Slide 4（アーキテクチャ概観）

- 話し方: 図の各ボックスを指しながら「業界を問わず同じ土台」であることを強調。技術的な詳細（実装言語、フレームワーク名等）には立ち入らない（技術セッションに譲る）

### Slide 5〜6（対応5業界・価値提案）

- 話し方: 参加者の業界に近い事例を優先して具体的に説明する
- **想定質問**: 「他の業界にも対応できますか？」
  - 回答例: 「はい、同じ仕組みで対応可能です。新しい業界向けの Industry Pack を追加する形になります。ただし、実際の業務データ・業界固有の規制要件の反映には、個別の検討・検証が必要です。」

### Slide 7（段階的な導入の考え方）

- **最重要の想定質問**: 「これは Copilot Studio や Microsoft 365 の実データと連携していますか？」
  - 回答例: 「いいえ、まだです。現時点では合成データによるローカルプレビュー環境のみが動作確認済みです。Microsoft 製品との連携は構想・検討段階であり、実際に接続して動いているわけではありません。導入を検討される際は、必ず Microsoft の最新の公式情報をご確認いただく前提でお話ししています。」
- 避けるべき表現: 「Foundry と統合しています」「Copilot Studio 上で動きます」など、現在形で実装済みであるかのように聞こえる表現。必ず「構想段階」「検討中」「検証が必要」という言葉を添える

### Slide 8（責任あるAI）

- 話し方: 「AI に自動判断させない事項」を業界ごとに具体的に一つ挙げると説得力が増す（例: 医療なら診断確定、金融なら口座凍結）
- **想定質問**: 「なぜ自動化しないのですか？もっと自動化した方が効率的では？」
  - 回答例: 「高リスクな判断は必ず人が最終確認する設計にしています。これは効率よりも、誤った自動判断による被害を防ぐことを優先した意思決定です。」

### Slide 9〜10（証明済みのこと・未検証のこと）

- このスライドは絶対に省略・駆け足で流さないこと。経営層が最も知りたいのは「今何ができて、何ができないか」の正確な線引き
- 話し方: Slide 9 を先に前向きに説明し、Slide 10 で「ただし正直にお伝えすると」という接続で切り替える
- **想定質問**: 「いつ実際に使えるようになりますか？」
  - 回答例: 「現時点で具体的な提供時期はお約束できません。次のステップは検証環境での接続確認であり、そこで得られた結果を踏まえてご相談させてください。」

### Slide 11〜12（ロードマップ・まとめ）

- 話し方: ロードマップは「順序」であり「確約された日程」ではないことを明確にする
- クロージング: 質問を受けた際に即答できない技術的な詳細は、技術セッション（Technical-Presentation.md）へ誘導してよい

## Technical Presentation 発表者ノート

### Slide 1〜3（タイトル・スコープ・全体像）

- 話し方: 「この資料に書かれている検証状況の注記は、誇張でも謙遜でもなく事実である」という前提を最初に共有する

### Slide 4〜5（Adapter パターン・mode enum）

- **想定質問**: 「`live` モードは実際に使われることがあるのですか？」
  - 回答例: 「型としては定義されていますが、現在のコードベースには `live` に到達する実行パスは存在しません。実際の製品 API 呼び出しコードは、呼び出す前に必ず例外を送出する設計になっています。これは製品仕様が未検証の状態で誤った前提のコードを書かないための意図的な制約です。」
- 避けるべき表現: 「Live Adapter は実装済みです」とだけ言って終わること。「実装済み」の意味（認証部分のみ実装・実 API 呼び出しは未実装）を必ず補足する

### Slide 6〜7（Industry Pack アーキテクチャ・追加ワークフロー）

- 話し方: 「一度、業界固有のロジックが共通コードに漏れ出してしまった経緯があり、設計を修正して業界非依存性を回復させた」という実体験を共有すると説得力が増す（詳細は内部参考セクションの ADR を参照、社外への詳細開示は不要）
- **想定質問**: 「業界を追加するのにどれくらいの工数がかかりますか？」
  - 回答例: 「プラットフォーム側の変更は不要ですが、Industry Pack 自体の作成（データ、ツール、シナリオ、ナレッジ、責任あるAI通知等）には相応の工数がかかります。正確な見積もりは対象業界の要件次第です。」

### Slide 8〜9（業務データ連携基盤・ツール契約）

- **想定質問**: 「本番環境ではどこにデプロイされますか？」
  - 回答例: 「コンテナ実行環境をターゲットとした構成をコードとして用意していますが、実際の Azure 環境へのデプロイはまだ実施していません（Slide 14 参照）。」

### Slide 10（Agent Response 契約）

- 話し方: 「模擬・合成データに関する開示文」と「責任あるAI通知文」が必須項目（オプションではない）であることを、型定義レベルの話として強調する。これは営業的な誇張ではなく設計上の技術的事実
- **想定質問**: 「なぜここまで厳格にスキーマを固定するのですか？」
  - 回答例: 「業界が変わっても回答の構造が変わらないようにするためです。また、開示文を省略した回答オブジェクトをそもそも構築できないようにすることで、開示漏れを設計レベルで防いでいます。」

### Slide 11〜12（責任あるAIの組み込み・評価エンジン）

- **想定質問**: 「評価エンジンは何を保証してくれるのですか？」
  - 回答例: 「開示文の有無や引用の有無など、機械的にチェックできる項目のみを保証します。根拠の妥当性など、人による判断が必要な項目については代理指標に留まり、人によるレビューの代替にはなりません。」
- 避けるべき表現: 「AIの回答品質を自動的に保証します」という言い切り。必ず「自動チェックできる範囲」の限定を添える

### Slide 13（テストカバレッジ）

- 話し方: テスト件数(137件)は「多い/少ない」の議論よりも、「カテゴリごとに何を保証しているか」の説明に重点を置く
- **想定質問**: 「テストが通っていれば本番投入して問題ないですか？」
  - 回答例: 「いいえ。現在のテストはローカルプレビュー環境での契約準拠・ロジックの正しさを保証するものであり、実環境での性能・セキュリティ・可用性を保証するものではありません。」

### Slide 14（デプロイアーキテクチャ）

- **想定質問**: 「コストはどれくらいですか？」
  - 回答例: 「現時点で具体的な数値はお出しできません。実 Azure 環境へのデプロイ自体を実施していないため、実測値がなく、価格は必ず Microsoft の最新の公式情報でご確認いただく前提です。」

### Slide 15（実装状況とロードマップ）

- このスライドも Executive 版の Slide 9〜10 と同様、絶対に省略しないこと
- クロージング: 質問が製品仕様（Microsoft 製品の価格・ライセンス・提供状況）に及んだ場合は、必ず「本アクセラレータ側では確定情報を持っていないため、Microsoft の公式情報を確認してほしい」と回答し、推測で答えない

## 全体を通じて避けるべき失敗（まとめ）

1. Live Adapter・Microsoft 製品連携について、現在形で「動いている」「統合されている」と言ってしまうこと
2. 「証明済みのこと／未検証のこと」のスライドを駆け足で流す、または省略すること
3. テスト件数や自動評価を「品質の完全な保証」であるかのように語ること
4. Microsoft 製品の価格・ライセンス・GA/Preview状態・リージョン提供状況について、確認せずに数値や状態を断定すること
5. デモの実行速度（数秒）を、そのまま「人が説明しながら進める所要時間」であるかのように語ること
